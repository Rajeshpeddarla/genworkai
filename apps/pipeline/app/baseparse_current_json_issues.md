# 3. Critical Issues

## Issue 1: A Gemini or SDK Error Was Stored as Document Content

Page 5 contains this block:

```json
{
  "id": "error_4",
  "type": "paragraph",
  "text": "Error: The `response.text` quick accessor only works when the response contains a valid `Part`, but none was returned...",
  "bbox": [0, 0, 1000, 1000]
}
```

### Why this is a serious problem

This text is not part of the original PDF.

It is an internal processing error that was incorrectly added to the extracted document content.

An API consumer could assume that this text appeared in the PDF. It may then be:

- Indexed in search
- Added to a vector database
- Returned in question-answering results
- Displayed to users
- Included in medical analysis
- Used by another AI model

This damages output reliability.

### Recommended fix

Do not insert internal errors inside `blocks`.

Use a page-level status:

```json
{
  "page_number": 5,
  "status": "failed",
  "retry_count": 3,
  "blocks": [],
  "error": {
    "code": "MODEL_RESPONSE_BLOCKED",
    "message": "The page could not be extracted.",
    "retryable": true
  }
}
```

### Required processing behaviour

```text
Gemini response received
        |
        v
Is valid structured JSON?
        |
   No --+--> Retry page
        |
        v
Retry failed?
        |
   Yes -+--> Mark page as failed
                |
                v
       Never add SDK errors to blocks
```

## Issue 2: The `bbox` Format Is Inconsistent

Two different formats are used.

### Format A

```json
"bbox": [128, 375, 142, 646]
```

### Format B

```json
"bbox": [[128, 375, 142, 646]]
```

Current counts:

```text
Flat four-value bbox: 158
Nested one-by-four bbox: 50
```

### Why this is a problem

An API consumer may write:

```javascript
const [x1, y1, x2, y2] = block.bbox;
```

That works for Format A but fails for Format B because the first element is another array.

This inconsistency causes:

- Runtime errors
- Additional normalization code
- Incorrect highlighting
- Broken page overlays
- Incorrect crop generation
- Integration complaints

### Recommended fix

Use one object format everywhere:

```json
"bbox": {
  "x1": 375,
  "y1": 128,
  "x2": 646,
  "y2": 142
}
```

An object is clearer than an array because each coordinate is named.

### Important coordinate-order warning

Based on the current values, the array may actually represent:

```text
[top, left, bottom, right]
```

rather than:

```text
[x1, y1, x2, y2]
```

For example:

```json
[128, 375, 142, 646]
```

appears to describe a short horizontal title located near the top of the page.

Therefore, BaseParse must explicitly document the coordinate order. Do not leave API consumers to guess.

Recommended standard:

```json
{
  "coordinate_system": {
    "origin": "top-left",
    "unit": "pixels",
    "bbox_format": "x1_y1_x2_y2"
  }
}
```

## Issue 3: Page Dimensions Use Different Coordinate Systems

The file contains these page dimensions:

```text
12 pages: 1000 × 1000
6 pages: 1000 × 1414
1 page: 1000 × 1395
```

### Why this may be a problem

The original PDF appears to contain pages with a similar portrait layout, but some pages are represented as square pages and others as portrait pages.

This suggests that different Gemini responses or image-processing paths may be using different coordinate systems.

If a client displays a bounding box over the original PDF page, the box may appear in the wrong location.

### Recommended fix

Choose one of these approaches.

### Option A: Preserve actual rendered pixel dimensions

```json
{
  "dimensions": {
    "width": 2000,
    "height": 2828,
    "unit": "pixels"
  }
}
```

All bounding boxes must use the same rendered image dimensions.

### Option B: Normalize every coordinate

```json
{
  "bbox": {
    "x": 0.128,
    "y": 0.265,
    "width": 0.518,
    "height": 0.102
  },
  "coordinate_system": {
    "origin": "top-left",
    "unit": "normalized",
    "range": [0, 1]
  }
}
```

Normalized coordinates are easier for consumers rendering at different screen sizes.

## Issue 4: Block Types Are Not Consistent

The current output uses:

```text
text
paragraph
header
heading
footer
table
list
diagram
```

The same kind of content is classified differently on different pages.

For example, `LABORATORY TEST REPORT` appears as:

```json
"type": "text"
```

on some pages, as:

```json
"type": "header"
```

on another page, and as:

```json
"type": "paragraph"
```

elsewhere.

### Why this is a problem

API consumers cannot reliably filter:

```javascript
blocks.filter(block => block.type === "header")
```

because some headers are classified as `text` or `paragraph`.

This reduces the usefulness of semantic parsing.

### Recommended fix

Define a strict enum and do not allow Gemini to invent values:

```text
title
heading
paragraph
list
table
figure
formula
header
footer
key_value
page_number
signature
barcode
checkbox
```

Example:

```json
{
  "type": "header",
  "subtype": "document_title",
  "text": "LABORATORY TEST REPORT"
}
```

Use server-side normalization after the Gemini response.

## Issue 5: Block IDs Are Not Unique Across the Document

Examples such as these are repeated:

```text
text_1
text_2
table_1
table_2
header_001
footer_001
```

There are 40 duplicated block ID values.

### Why this is a problem

A consumer may build an index:

```javascript
blockMap[block.id] = block;
```

When IDs repeat, a later page overwrites an earlier block.

Duplicate IDs also make it difficult to:

- Create citations
- Link table images
- Reference blocks from another API
- Store blocks in a database
- Build relationships
- Update or correct individual blocks

### Recommended fix

Make block IDs unique at document level:

```text
page_001_block_001
page_001_table_002
page_006_formula_004
```

Example:

```json
{
  "id": "page_003_table_002",
  "page_number": 3,
  "type": "table"
}
```

A UUID can also be used:

```json
{
  "id": "blk_7df0d82c"
}
```

Human-readable page-based IDs are easier for debugging.

## Issue 6: Tables Are Mostly Returned as Flattened Text

A current table looks like this:

```json
{
  "type": "table",
  "text": "Test, Result, Unit, Biological Ref. Interval; Hemoglobin, 14.5, g/dL, 13.0 - 16.5..."
}
```

### What is good

The flattened text is useful for:

- Full-text search
- Vector embedding
- Summarization
- Basic display

### What is missing

It does not reliably preserve:

- Columns
- Rows
- Individual cells
- Row spans
- Column spans
- Headers
- Cell coordinates
- Merged cells
- Footnotes

### Why this matters

A developer cannot safely convert the current text into:

- CSV
- Excel
- HTML tables
- Database rows
- Statistical data
- Medical result records

For example, a medical table may contain:

```text
Neutrophils, 73, %, 7716, /cmm, 40-80, 2000-6700
```

Without a proper cell structure, it is unclear which value belongs to which column.

### Recommended fix

Return both searchable text and structured data:

```json
{
  "id": "page_001_table_003",
  "type": "table",
  "text": "WBC Count 10570 /cmm...",
  "table": {
    "columns": [
      {
        "index": 0,
        "name": "Test"
      },
      {
        "index": 1,
        "name": "Result"
      },
      {
        "index": 2,
        "name": "Unit"
      },
      {
        "index": 3,
        "name": "Reference Interval"
      }
    ],
    "rows": [
      {
        "index": 0,
        "cells": [
          {
            "column_index": 0,
            "text": "WBC Count"
          },
          {
            "column_index": 1,
            "text": "10570"
          },
          {
            "column_index": 2,
            "text": "/cmm"
          },
          {
            "column_index": 3,
            "text": "4000 - 10000"
          }
        ]
      }
    ]
  }
}
```

You may also return:

```json
{
  "markdown": "| Test | Result | Unit | Reference |",
  "html": "<table>...</table>",
  "csv": "Test,Result,Unit,Reference"
}
```

## Issue 7: `image_url` Is Inconsistent

Some table blocks contain:

```json
"image_url": "https://.../table_1.png"
```

Some contain:

```json
"image_url": null
```

Some do not contain the field at all.

Current counts:

```text
Blocks containing image_url: 30
image_url values that are null: 9
```

### Why this is a problem

A client cannot tell whether:

- No image was required
- Image extraction failed
- Upload failed
- The URL expired
- The image is still processing
- The field was accidentally omitted

### Recommended fix

Use an explicit asset object:

```json
{
  "asset": {
    "status": "available",
    "type": "table_crop",
    "mime_type": "image/png",
    "storage_key": "documents/doc_123/pages/1/table_1.png",
    "url": "short-lived-signed-url",
    "expires_at": "2026-07-30T12:00:00Z"
  }
}
```

When unavailable:

```json
{
  "asset": {
    "status": "not_generated"
  }
}
```

When extraction failed:

```json
{
  "asset": {
    "status": "failed",
    "error_code": "TABLE_CROP_FAILED"
  }
}
```

## Issue 8: Public Asset URLs Expose Sensitive Content

The JSON contains public Supabase URLs for table images.

For medical documents, those crops may contain:

- Patient names
- Dates of birth
- Lab IDs
- Medical results
- Clinic information
- Doctor information

### Why this is risky

Anyone with the public URL may be able to access the asset.

Even when the URL is difficult to guess, it should not be treated as secure.

### Recommended fix

Use:

- Private storage buckets
- Row-level access controls
- Short-lived signed URLs
- Per-user authorization
- Automatic asset deletion
- Configurable document retention

Do not return permanent public URLs.

Example:

```json
{
  "asset": {
    "storage_key": "private/doc_123/page_1/table_1.png",
    "download_url": "signed-url",
    "expires_in_seconds": 900
  }
}
```

# 4. Important Quality Issues

## Issue 9: No Confidence Score

The current blocks do not consistently return extraction confidence.

### Why this matters

Not every page has the same quality.

Confidence is useful for:

- Triggering retries
- Showing warnings
- Sending difficult pages to a stronger model
- Requesting human review
- Comparing output quality
- Detecting poor OCR

### Recommended fix

Return confidence at multiple levels:

```json
{
  "page_confidence": 0.94,
  "blocks": [
    {
      "id": "page_001_table_002",
      "confidence": 0.91,
      "text_confidence": 0.96,
      "layout_confidence": 0.88
    }
  ]
}
```

Do not rely only on Gemini to generate an arbitrary confidence score. Combine model signals with validation rules where possible.

The laboratory name, doctor signatures, authentication note, address, and page number appear repeatedly on many pages.

### Why this matters

If the complete JSON is embedded for RAG, repeated boilerplate will:

- Waste tokens
- Pollute search results
- Reduce retrieval quality
- Cause repeated answers
- Increase storage
- Bias summaries

### Recommended fix

Keep page-level header and footer blocks, but also detect repeated boilerplate.

## Issue 13: No Schema Version

The output does not contain a version such as:

```json
"schema_version": "1.0"
```

### Why this matters

BaseParse will change over time.

You may later:

- Change the bounding-box format
- Add table cells
- Rename block types
- Add confidence
- Add formulas
- Add relationships
- Change asset fields

Without schema versioning, existing clients may break unexpectedly.

### Recommended fix

Add:

```json
{
  "schema_version": "1.0.0"
}
```

Follow semantic versioning:

```text
Patch: Backward-compatible correction
Minor: Backward-compatible field addition
Major: Breaking schema change
```

# 6. Recommended Validation Rules

Every page result should pass these checks before it is merged.

## JSON checks

```text
Response is valid JSON
Response contains no markdown fences
Required fields are present
No unexpected top-level fields when strict mode is enabled
```

## Page checks

```text
Returned page number matches requested page
Width and height are positive
Status is valid
Blocks is an array
```

## Block checks

```text
Block ID is document-wide unique
Block type is from the allowed enum
Text is a string
Bounding box has exactly four valid coordinates
Coordinates fit within page dimensions
Reading order is a positive integer
Confidence is between 0 and 1
```

## Content checks

```text
No internal SDK error text
No safety error text
No obvious response truncation
Non-empty page does not return zero blocks
Table blocks contain rows/cells when table extraction is enabled
Formula blocks contain LaTeX when formula extraction is enabled
```

## Asset checks

```text
Private storage key exists
Signed URL is generated only after authorization
No permanent public URL is returned
Asset status is explicit
```

# 8. Priority Order for Fixing the Current Output

## Priority 1 — Must fix before public launch

1. Prevent internal Gemini or SDK errors from entering document content.
2. Add page-level retry and failure status.
3. Standardize the `bbox` format.
4. Document the coordinate order and origin.
5. Standardize page dimensions.
6. Make block IDs unique across the document.
7. Use private storage instead of permanent public asset URLs.
8. Add `schema_version`.

## Priority 2 — Required for a strong document-parsing API

1. Standardize block types.
2. Return structured table rows and cells.
3. Add reading order.
4. Add confidence scores.
5. Add warnings.
6. Add job and processing metadata.
7. Extract key-value sections as structured fields.
8. Separate repeated headers and footers from main searchable content.

## Priority 3 — Important for research papers and exam documents

1. Add formula objects with LaTeX.
2. Add figure-caption relationships.
3. Add question and option block types.
4. Add table cell coordinates.
5. Add document-level sections and hierarchy.
6. Add redaction and sensitive-data detection.

# 9. Final Assessment

The current JSON is a good proof of concept because it already provides:

- Page-level separation
- Text extraction
- Table detection
- Layout coordinates
- Image references
- Basic semantic block types

However, it is not yet a stable public API format.

The most serious current weaknesses are:

```text
Internal error included as document text
Inconsistent bounding-box structure
Unclear coordinate order
Inconsistent page dimensions
Duplicate block IDs
Inconsistent semantic block types
Flattened tables instead of rows and cells
Public URLs for sensitive medical assets
```
